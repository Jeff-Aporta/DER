## Qué cambia entre motores (todo dentro del `Engine`)

| | PG / PGlite | SQLite | MySQL | MSSQL |
|---|---|---|---|---|
| tipos DDL | varchar/numeric/boolean/timestamptz/jsonb | text/integer/real/numeric | varchar/decimal(18,6)/tinyint(1)/datetime(3)/json | nvarchar/decimal(18,6)/bit/datetime2/nvarchar(max) |
| bool | boolean | 0/1 | 0/1 | bit |
| date / time | `::text` | texto | `date_format` / `time_format` | `convert(varchar, …, 23/108)` |
| json | jsonb | texto + `JSON.parse` | json | texto + `JSON.parse` |
| relación 1:1 | `row_to_json` | `json_object` | `json_object` | `for json path, without_array_wrapper` |
| relación 1:N | `coalesce(json_agg, '[]')` | `json_group_array(json_object)` | `coalesce(json_arrayagg(json_object), json_array())` | `isnull((… for json path), '[]')` |
| `ilike` | `ilike` | `lower(x) like lower(?)` | `lower(x) like lower(?)` (sin `escape`: backslash por defecto) | `lower(x) like lower(?)` |
| paginación | `limit/offset` | `limit/offset` | `limit/offset` | `offset … rows fetch next … rows only` (siempre, también como subconsulta) |
| escrituras | `returning` | `returning` | insertar y releer por pk (`insertId` para autoincrement) | `output inserted.* / deleted.*` |
| autoincrement | `generated by default as identity` | `integer primary key autoincrement` | `auto_increment` | `identity` |
| `if not exists` | sí | sí | sí | no: se consulta `sys.tables` / `sys.indexes` antes de crear |

Los POJOs normalizan lo que llega (casteos), así el resultado es idéntico en todos los motores. `tests/server/server.test.ts` corre los mismos casos en SQLite y PostgreSQL (PGlite); `tests/server/engines.test.ts` compila el SQL de MySQL y MSSQL sin conexión y prueba el driver SQLite asíncrono.

## `seed()`

`ctrl.seed()` o `db.seed()` (todos los registrados, en orden): `CREATE TABLE IF NOT EXISTS` a partir de las columnas persistidas del POJO: tipos, `NOT NULL`, `UNIQUE`, `DEFAULT`, pk simple o compuesta y autoincrement. **Crea también las secuencias (`createSequence`/`nextValue`) y los índices (`ensureIndexes`).** No crea FKs (la integridad la vigila el DER por código). También crea la tabla de configuración de las entidades (`plural/cfg`) si el server la define. El nombre de la tabla sale de `config.table` o, por defecto, de la entidad (el plural).

## Caso de identificadores

`identifierCase: "preserve" | "lower" | "upper"` en el `Database` (default) o en cada controller. Se aplica al nombre de tabla y de columnas, y los resultados siempre vuelven con los nombres de campo del POJO (alias). Todas las referencias van entre comillas, así que el caso es literal en todos los motores.

## `syncSchema()`: sincronizar la tabla con el POJO (migraciones)

Opcional, para cuando el POJO cambia y la tabla ya tiene datos:

```ts
const plan = await productos.syncSchema({ dryRun: true });   // { added, dropped, created, ... } sin tocar nada
await productos.syncSchema({
  migrate: (anterior) => (anterior["viejo"] ? { meta: { origen: anterior["viejo"] } } : undefined),
  keepExtra: false,   // default: se eliminan las columnas que el POJO ya no tiene
});
```

1. **Inventario** de los getters/setters del POJO (`pojoAccessors()`): toda columna persistida del schema debe tener su accessor (si no, error).
2. **Introspección** de la tabla (Kysely, cualquier motor). Si no existe, se crea (`seedTable`).
3. **Agrega** las columnas que faltan (con su default) y **conserva** los valores de las que coinciden.
4. **Migra:** `migrate(anterior)` recibe cada fila con las columnas viejas todavía presentes y retorna los valores a escribir (o `undefined` para no tocarla).
5. **Elimina** las columnas que el POJO ya no tiene (salvo `keepExtra`).

Todo va en una transacción. No migra la pk: si cambió, se recrea la tabla. Las columnas nuevas quedan nullables, salvo que tengan default.

## Secuencias

Se declaran en la columna, en la definición compartida (JSON), así el cliente ya no exige el valor en el POST. El servidor lo genera al insertar si no viene; si viene, lo respeta.

```ts
columns: {
  ifactura:    { type: "int", pk: true, sequence: { name: "seq_factura", start: 1000 } }, // global, nombrada
  numero:      { type: "string", sequence: { name: "seq_numero", pattern: "FAC-{n:5}" } }, // FAC-00001
  consecutivo: { type: "int", sequence: { scope: ["iempresa"] } },                         // 1, 2… por empresa
  ilinea:      { type: "int", pk: true, sequence: { scope: ["ipedido"] } },                // línea dentro del pedido
  codigo:      { type: "string", pk: true, sequence: { base: 36 } },                        // "1", "2", … "z", "10": autoincrement quemado en base 36
  folio:       { type: "string", sequence: { scope: ["iempresa"], base: 16, pattern: "F-{n:3}" } }, // F-001 … F-00f, F-010
  ticket:      { type: "string", sequence: true },                                           // base 10 como texto: "1", "2"…
}
```

| Tipo | PG / MSSQL | SQLite / MySQL |
|---|---|---|
| global (`name`, `start`, `increment`) | `CREATE SEQUENCE` + `nextval` / `next value for` | tabla `_sequences` + `UPDATE … RETURNING` / `last_insert_id(expr)` (atómicos) |
| por ámbito (`scope`) | máximo del grupo + incremento, dentro de la transacción del insert | igual |
| `pattern` (`{n}`, `{n:ancho}`) | número formateado para columnas string | igual |

- **Base (`base`, 2..36, default 10):** el número se quema en esa base. Base > 10 exige una columna `string`/`text` (`as: "string"`, el default en columnas de texto); en una columna numérica solo cabe base 10 (`as: "number"`). Cualquier otra combinación es un error al definir el schema. En las secuencias por ámbito, el máximo se lee en esa base del último tramo alfanumérico del valor guardado (lo que deja el patrón al final).
- Las secuencias globales se crean en `seed()` / `syncSchema()`. Si `name` se repite, la secuencia se comparte entre columnas o tablas.
- Como en todo motor, una secuencia global no retrocede si la transacción falla (puede dejar huecos).
- La secuencia por ámbito calcula el máximo dentro de la transacción del POST. Con alta concurrencia sobre el mismo grupo, conviene respaldarla con un índice único (ver abajo): un choque falla en lugar de duplicar.

## Índices

```ts
new ServerController(FacturaEntity, {
  db, table: "facturas",
  indexes: [{ columns: ["iempresa", "consecutivo"], unique: true }],   // ux_facturas_iempresa_consecutivo
  autoIndexes: true,                                                   // default
});
```

- **Automáticos (`autoIndexes`, default activo):**
  - la FK local de cada relación 1:1 (`productos.icategoria`, `pedido_lineas.iproducto`);
  - las llaves remotas de cada detalle 1:N de la misma base, en la tabla del detalle.

  Se omiten las columnas que ya son prefijo de la pk (`pedido_lineas.ipedido`) y la FK de una sola columna `unique`.
- **Explícitos:** `indexes: [{ columns, unique?, name? }]`, con nombres por defecto `ix_<tabla>_<columnas>` o `ux_…` si es único.
- Se crean con `CREATE [UNIQUE] INDEX IF NOT EXISTS` (o su equivalente en MSSQL) en `seed()` y `syncSchema()`. Los índices que una relación 1:N pide sobre la tabla del detalle los crea esa tabla al sembrarse, así no importa el orden del seed.
- Utilidades: `resolvedIndexes()`, `detailIndexes()`, `requestedIndexes()` y `ensureIndexes()`.
