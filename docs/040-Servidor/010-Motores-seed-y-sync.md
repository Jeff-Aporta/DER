# Motores SQL

[← índice](../README.md) · contrato `Engine` en `src/02 controllers/server/schemas.ts`

| Carpeta | Fábrica | Driver | Dependencias extra |
|---|---|---|---|
| `server/sqlite/` | `sqliteDatabase(path = ":memory:", { identifierCase })` | `node:sqlite` (nativo en Deno 2 y Node 22+) | — |
| `server/pg/` | `pgDatabase(pool, { identifierCase })` | pool compatible con `pg`, lo aporta el consumidor | tu pool |
| `server/pglite/` | `pgliteDatabase(pglite?, { identifierCase })` | PGlite (Postgres WASM embebido) | `@electric-sql/pglite` |

Cualquier dialecto de Kysely sirve con `new Database({ engine, dialect, identifierCase })`.

## Qué cambia entre motores (todo dentro del `Engine`)

| | PG | SQLite |
|---|---|---|
| tipos DDL | varchar/numeric/boolean/timestamptz/jsonb | text/integer/real/numeric |
| bool | boolean | 0/1 |
| date / time | se leen `::text` (sin corrimiento de zona) | texto |
| json | jsonb (`readJson` lo deja como objeto) | texto + `JSON.parse` |
| relación 1:1 | `row_to_json` | `json_object` |
| relación 1:N | `coalesce(json_agg, '[]')` | `json_group_array(json_object)` |
| `ilike` | `ilike` | `lower(x) like lower(?)` |
| autoincrement | `generated by default as identity` | `integer primary key autoincrement` |

Los POJOs normalizan lo que llega (casteos), así el resultado es idéntico en ambos motores. Los tests de `tests/server.test.ts` lo verifican corriendo los mismos casos en los dos.

## `seed()`

`ctrl.seed()` o `db.seed()` (todos los registrados, en orden): `CREATE TABLE IF NOT EXISTS` a partir de las columnas persistidas del POJO: tipos, `NOT NULL`, `UNIQUE`, `DEFAULT`, pk simple o compuesta y autoincrement. No crea FKs ni índices; las tablas externas de `/cfg` las crea el consumidor.

## Caso de identificadores

`identifierCase: "preserve" | "lower" | "upper"` en el `Database` (default) o en cada controller. Se aplica al nombre de tabla y de columnas, y los resultados siempre vuelven con los nombres de campo del POJO (alias). Todas las referencias van entre comillas, así que el caso es literal en ambos motores.

## Agregar un motor (p. ej. MySQL)

1. `src/02 controllers/server/mysql/engine.ts`: implementar `Engine` (`columnType`, `selectExpr`, `toDb`, `readJson`, `jsonOne`, `jsonMany`, `ilike`).
2. `src/02 controllers/server/mysql/mod.ts`: fábrica con el dialecto de Kysely, `export * from "../mod.ts"` y la cabecera con el enlace a `docs/README.md`.
3. Registrar su dependencia permitida en `tests/arch.test.ts` y agregar el motor al arreglo `ENGINES` de `tests/server.test.ts`.

## `syncSchema()`: sincronizar la tabla con el POJO (migraciones)

Opcional, para cuando el POJO cambia y la tabla ya tiene datos:

```ts
const plan = await productos.syncSchema({ dryRun: true });   // { added, dropped, created, ... } sin tocar nada
await productos.syncSchema({
  migrate: (anterior) => (anterior["viejo"] ? { meta: { origen: anterior["viejo"] } } : undefined),
  keepExtra: false,   // default: se eliminan las columnas que el POJO ya no tiene
});
```

1. **Inventario** de los getters/setters del POJO (`pojoAccessors()`): toda columna persistida del schema debe tener su accessor (si no, error).
2. **Introspección** de la tabla (Kysely, cualquier motor). Si no existe, se crea (`seedTable`).
3. **Agrega** las columnas que faltan (con su default) y **conserva** los valores de las que coinciden.
4. **Migra:** `migrate(anterior)` recibe cada fila con las columnas viejas todavía presentes y retorna los valores a escribir (o `undefined` para no tocarla).
5. **Elimina** las columnas que el POJO ya no tiene (salvo `keepExtra`).

Todo va en una transacción. No migra la pk: si cambió, se recrea la tabla. Las columnas nuevas quedan nullables, salvo que tengan default.

## Secuencias

Se declaran en la columna, en la definición compartida (JSON), así el cliente ya no exige el valor en el POST. El
servidor lo genera al insertar si no viene; si viene, lo respeta.

```ts
columns: {
  ifactura:    { type: "int", pk: true, sequence: { name: "seq_factura", start: 1000 } }, // global, nombrada
  numero:      { type: "string", sequence: { name: "seq_numero", pattern: "FAC-{n:5}" } }, // FAC-00001
  consecutivo: { type: "int", sequence: { scope: ["iempresa"] } },                         // 1, 2… por empresa
  ilinea:      { type: "int", pk: true, sequence: { scope: ["ipedido"] } },                // línea dentro del pedido
  codigo:      { type: "string", sequence: true },                                          // <tabla>_<campo>_seq
}
```

| Tipo | PG | SQLite |
|---|---|---|
| global (`name`, `start`, `increment`) | `CREATE SEQUENCE` + `nextval` | tabla `_sequences` + `UPDATE … RETURNING` (atómico) |
| por ámbito (`scope`) | máximo del grupo + incremento, dentro de la transacción del insert | igual |
| `pattern` (`{n}`, `{n:ancho}`) | número formateado para columnas string | igual |

- Las secuencias globales se crean en `seed()` / `syncSchema()`. Si `name` se repite, la secuencia se comparte
  entre columnas o tablas.
- Como en todo motor, una secuencia global no retrocede si la transacción falla (puede dejar huecos).
- La secuencia por ámbito calcula el máximo dentro de la transacción. Con alta concurrencia sobre el mismo grupo,
  conviene respaldarla con un índice único (ver abajo): un choque falla en lugar de duplicar.

## Índices

```ts
new ServerController(Factura, {
  db, table: "facturas",
  indexes: [{ columns: ["iempresa", "consecutivo"], unique: true }],   // ux_facturas_iempresa_consecutivo
  autoIndexes: true,                                                   // default
});
```

- **Automáticos (`autoIndexes`, default activo):**
  - la FK local de cada relación 1:1 (`productos.icategoria`, `pedido_lineas.iproducto`);
  - las llaves remotas de cada detalle 1:N de la misma base, en la tabla del detalle.

  Se omiten las columnas que ya son prefijo de la pk (`pedido_lineas.ipedido`) y la FK de una sola columna
  `unique`.
- **Explícitos:** `indexes: [{ columns, unique?, name? }]`, con nombres por defecto `ix_<tabla>_<columnas>` o
  `ux_…` si es único.
- Se crean con `CREATE [UNIQUE] INDEX IF NOT EXISTS` en `seed()` y `syncSchema()`. Los índices que una relación
  1:N pide sobre la tabla del detalle los crea esa tabla al sembrarse, así no importa el orden del seed.
- Utilidades: `resolvedIndexes()`, `detailIndexes()`, `requestedIndexes()` y `ensureIndexes()`.
